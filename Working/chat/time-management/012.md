Primary Domain Object – Zeitposition
Zweck
Eine Zeitposition repräsentiert einen fachlichen Geschäftsvorfall innerhalb eines Zeitkontos.
Sie dokumentiert die Entstehung, Veränderung oder den Verbrauch einer bestimmten Zeitmenge.
Jede Zeitposition bleibt dauerhaft Bestandteil der fachlichen Historie.
________________________________________
Fachliche Verantwortung
Eine Zeitposition ist verantwortlich für:
•	die Dokumentation eines fachlichen Geschäftsvorfalls, 
•	die Zuordnung zu genau einem Zeitkonto, 
•	die Zuordnung zu genau einer Anspruchsart, 
•	die Dokumentation der zugehörigen Zeitmenge, 
•	die Bereitstellung der Grundlage für Bewertung und Ausgleich. 
________________________________________
Eigenschaften
Eine Zeitposition besitzt insbesondere:
•	eine eindeutige fachliche Identität, 
•	einen Zeitpunkt bzw. Gültigkeitsbezug, 
•	eine Anspruchsart, 
•	eine Zeitmenge, 
•	einen aktuellen fachlichen Zustand. 
________________________________________
Lebenszyklus
Eine Zeitposition entsteht durch einen fachlichen Geschäftsprozess.
Im weiteren Lebenszyklus kann sie:
•	vollständig oder teilweise ausgeglichen werden, 
•	bewertet werden, 
•	aufgrund geänderter fachlicher Rahmenbedingungen angepasst werden, 
•	historisch abgeschlossen werden. 
Die ursprüngliche Zeitposition bleibt dabei Bestandteil der fachlichen Historie.
________________________________________
Business Rules
•	Eine Zeitposition gehört genau einem Zeitkonto. 
•	Eine Zeitposition gehört genau einer Anspruchsart. 
•	Eine Zeitposition darf positive oder negative Zeitmengen enthalten. 
•	Eine Zeitposition darf vollständig oder teilweise ausgeglichen werden. 
•	Der aktuelle Bestand einer Anspruchsart ergibt sich aus der Summe der noch nicht ausgeglichenen Zeitpositionen.

Primary Configuration Object – Working Time Model
Purpose
A Working Time Model defines the business framework that governs how working time is interpreted within an employment relationship.
It does not create business transactions itself.
Instead, it defines the business rules that are applied when business transactions are created or evaluated.
________________________________________
Responsibilities
A Working Time Model is responsible for defining:
•	the regular working time pattern, 
•	the reference working time for valuation purposes, 
•	the rules required to derive entitlements, 
•	the assignment of applicable business strategies. 
________________________________________
Explicitly not responsible for
A Working Time Model does not:
•	create business transactions, 
•	calculate balances, 
•	perform automatic settlement, 
•	perform valuations, 
•	store historical balances. 
Those responsibilities belong to other domain objects or business processes.
________________________________________
Relationships
A Working Time Model may reference one or more business strategies, for example:
•	Accrual Strategy 
•	Valuation Strategy 
•	Settlement Strategy 
•	Carry Forward Strategy 
The exact set of referenced strategies depends on the business requirements and is defined in the Solution Design.

# Contributing Guidelines

## Purpose

This document defines the working principles for all contributors to the ERP DevCon Engineering Repository.

The objective is to ensure that documentation, architectural decisions and engineering knowledge remain consistent, maintainable and traceable throughout the lifetime of the repository.

---

# General Principles

Every contribution shall improve the quality of the repository.

Contributors are expected to prioritize

- clarity
- consistency
- maintainability
- traceability
- long-term usability

over short-term convenience.

---

# Documentation Language

The official documentation language is English.

Business terminology shall remain consistent across all documents.

If a business term has been defined in the glossary, the glossary definition shall always be used.

---

# Single Source of Truth

Every business rule, architectural principle or technical standard shall have exactly one authoritative definition.

Duplicate documentation shall be avoided.

Documents shall reference existing definitions instead of copying them.

---

# Repository Structure

Documentation shall always be stored in the appropriate section of the repository.

Company-wide principles belong to

/company-guide

Architecture decisions belong to

/architecture/adr

Technical standards belong to

/standards

Reusable document templates belong to

/templates

Business terminology belongs to

/glossary

Product-specific documentation belongs to

/products

Research material belongs to

/research

Archived documentation belongs to

/archive

---

# Markdown

Markdown is the authoritative source format.

Generated Word and PDF documents are considered publication formats.

The Markdown sources always take precedence.

---

# Branch Strategy

Documentation shall never be developed directly in the main branch.

Development takes place in dedicated working branches.

Examples

company-guide

time-management

business-central

research

Additional feature branches may be created whenever appropriate.

---

# Commit Messages

Each commit shall represent one logical change.

Commit messages should be short, descriptive and written in English.
